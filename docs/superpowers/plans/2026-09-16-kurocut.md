**Goal:** 在 Windows + RTX 5080 + 32GB RAM 上，结合日语语义、声音和画面理解直播情境，自动选择高光、编排适合内容的镜头与动效，生成可审改的竖屏短片，保留中文审片说明与来源时间戳。

**Architecture:** Python 单机串行流水线；faster-whisper 负责日语转录，文本模型提供初筛基线，多模态模型结合实际视频与原声定位事件并输出剪辑决策，FFmpeg/ASS 执行。JSON 保存证据、决策与产物，Streamlit 用于审改。一个模型分步骤调用即可，不搭建多代理框架。最终目标是一键生成随内容变化的完整草稿。

**Tech Stack:** Python 3.11、FFmpeg/ffprobe（libass、libx264、NVENC）、faster-whisper/CTranslate2、Python 标准库、可选单一文本 API SDK、Streamlit（到审稿阶段才安装）。

## Global Constraints

- 用户硬件：“Windows 32G内存”，一台 RTX 5080；用户不懂日语，但有懂日语的朋友。
- 用户盈利目标：“两种都想做”，即接单交付与自营账号；海报 300 元/份尚未经客户确认。
- 第一版交付 45–75 秒、1080×1920、H.264/yuv420p/AAC 的日语原声短片。基础链路可先测试 30fps，动效质量验收输出 60fps，与本地参考一致；不对低帧率原片默认做 AI 补帧。客户若要求严格一分钟，则最大时长为 60 秒。
- 参考片是质量范本，不是固定剧情、字幕内容或动画时序。Task 3 的纯文本基线不能算完整目标通过；Task 3B 多模态理解与自动编排为必需阶段。
- 面向日本受众时烧录日语字幕，中文释义只在审稿页/附属文件。保留原声，不默认配音。
- 所有源码和脚本兼容 Windows 路径；当前 macOS 仅能做文档或非 GPU 检查，不能标记 Windows/GPU 验收通过。
- 第一版只接收本地、可使用的视频；下载器、直播监控和平台发布不是首版依赖。
- 不训练模型，不做多代理剪辑、通用插件框架、数据库、队列服务器或完整视频编辑器。
- 固定主播版式使用手动校准 ROI（裁切区域），切换布局或遮挡时标记复核，不盲目人脸追踪。
- 推理与渲染串行；FP16 ASR 起步，不默认 Blackwell 支持所用版本的 INT8。
- 文本/多模态 API 的地址、模型、可上传素材范围和费用上限显式配置；密钥只从环境变量读取。不要假定编码助手的模型名是可调用的生产 API 型号。尚未选择服务或配置上传范围时只运行离线检查。
- 一个任务成功后再进入下一个；每个非平凡逻辑保留最小可运行检查，不铺开测试框架。

## 验收材料：先用一场完整回放

用户明确提出用某场直播回放实验。可行，且应从完整回放开始，而非只识别已经剪好的 Shorts。

首场建议：1–3 小时、单人日语《鸣潮》或相同垂类直播、声音清楚、人物位置固定、包含聊天与游戏反应。尚未收到具体回放链接或本地路径；这不影响代码的合成媒体测试，但真实高光质量验收必须等真实素材。

建立 `runs/pilot-01/`，至少留下：

```text
source.json             原片路径、来源说明、SHA256、时长、音视频流信息
transcript.json         原片绝对时间轴上的日语识别结果和风险标记
candidates.json         候选片段、证据 ID、中文理由、评分项
edits/clip-001.json      每条短片的镜头、字幕、模板和审核状态
previews/clip-001.mp4    低码率预览，未通过审核时也允许输出
exports/clip-001.mp4     经审核的交付成片
exports/clip-001.ja.srt  日语字幕；同时保存 ASS 和中文审片文本
metrics.json            耗时、费用、峰值显存记录、人工计时
review.json             人的通过/退回决定及原因
```

让朋友事先独立标 3–5 个高光，保存 `evaluation/pilot-01-human.json`。**该文件不进入 LLM 输入，也不作为默认选段配置**。初次输出冻结后再比较；调试用第一场，最终用第二场从未调试过的回放复测。

```json
{
  "source_sha256": "由真实原片计算",
  "moments": [
    {"start": 120.0, "end": 168.0, "reason_zh": "示例：铺垫之后发生反转，主播有连续反应"}
  ]
}
```

上面的区间只展示数据格式，不是某场直播的真实高光。用户未提供原片前，不能伪造基准标注。

评估口径：

- **候选可用率**：朋友判断可剪候选数 / AI 输出候选数；同时记 Top 10 中可用数量，目标至少 3 条。若只有 2 条候选就记 2 条，不补假片段。
- **人工高光命中率**：3–5 个预标高光中被候选充分覆盖的个数 / 预标个数；覆盖至少人工区间的 50% 可作自动粗筛，朋友仍要确认包袱是否完整。人工标注不是穷尽答案，AI 新找到的好片段也计可用。
- **字幕质量**：随机抽取 100 个有语音句子（不足则全量），朋友标记关键事实/人名/否定/说话人错误和一般文字错误；没有人工真值就不报“准确率 99%”。
- **时间对齐**：抽查 20 个句子，目标至少 90% 字幕起点误差不超过 300ms。该阈值是项目目标，不是宣称现成模型达到。
- **最终成片**：至少 3 条不同情境的片子，日语语义、切点、主体、字幕可读性、原声同步均通过人工审核；正式发布前逐条看完。
- **业务计时**：记录所有尝试的人工分钟数、重做次数、拒稿、付费与到账。看回放找原片的时间也要计入。

## 文件结构与固定接口

初始目录无代码。按阶段创建，不提前创建空模块：

| 文件 | 首次创建任务 | 责任 |
| --- | --- | --- |
| `kurocut.py` | 1 | argparse 命令、项目读写、阶段调用及恢复 |
| `media.py` | 1 | ffprobe、裁切、时间映射、ASS、渲染与成品检查 |
| `tests/test_pipeline.py` | 1 | 标准库 unittest 的紧凑回归检查 |
| `README.md`、`.gitignore` | 1 | Windows 实际运行方法、忽略密钥/素材/缓存 |
| `requirements.txt` | 2 | 实测通过的直接依赖版本 |
| `asr.py` | 2 | 日语识别、源时间戳与识别风险 |
| `editor.py` | 3 | 分窗、API 调用、候选校验、编辑草稿 |
| `director.py` | 3B | 音视频事件理解、证据校验、按内容编排 |
| `presets/default.json` | 4 | 一个经过校准的版式和字幕样式配置 |
| `app.py` | 4 | 本地审稿、修改、重新预览、审批 |
| `benchmark.py` | 5 | 单场/留出场实验记录与验收汇总 |

接口以 JSON 可表达的 dict/list 为主；无类继承、无 provider 工厂。关键函数统一使用以下名字，避免任务间改名：

```python
# media.py
def probe(source: Path) -> dict: ...
def validate_edit(edit: dict, duration: float) -> None: ...
def remap_interval(start: float, end: float, shots: list[dict]) -> list[tuple[float, float]]: ...
def render(source: Path, edit: dict, output: Path, encoder: str) -> None: ...
def verify_video(output: Path, expected_duration: float) -> dict: ...

# asr.py
def transcribe(source: Path, model_name: str = "large-v3") -> dict: ...

# editor.py
def find_candidates(transcript: dict, settings: dict) -> list[dict]: ...
def make_edit(candidate: dict, transcript: dict, preset: dict) -> dict: ...
```

这些签名定义约定，不是把省略号提交为代码。实际模块只在对应任务中实现。

`transcript.json` 用原片绝对秒数。每段 `id` 唯一，保留 `start/end/text_ja/words/flags`。不要把模型吐出的“很有把握”转换成客观准确率。

`candidates.json` 每条包含 `id/start_segment_id/end_segment_id/evidence_segment_ids/reason_zh/score/flags`；时间范围由真实转录 ID 查表计算，并做边界扩展。允许 `[]`。

`edit.json` 最小示例（坐标必须由原片校准，以下是 1920×1080 合成素材的测试值）：

```json
{
  "version": 1,
  "review_status": "draft",
  "source_sha256": "由原片计算",
  "shots": [{"start": 120.0, "end": 168.0, "layout": "split"}],
  "game_roi": [0, 0, 1920, 1080],
  "avatar_roi": [1440, 480, 480, 600],
  "subtitles": [{"start": 1.0, "end": 3.0, "text_ja": "これはテストです", "note_zh": "这是测试字幕", "style": "normal"}],
  "width": 1080,
  "height": 1920,
  "fps": 30
}
```

**镜头 start/end 永远是源片时间，字幕 start/end 永远是最终成片时间。** 第一版每条候选以连续区间为主，布局变化可拆成相邻 shots；删去间隙或做长片时也遵循同一映射规则。禁止用“减去第一个切点”处理多段拼接的全部字幕。

class PipelineTest(unittest.TestCase):

## Task 2：日语转录和可核对字幕

**Interfaces:** `transcribe(source, model_name)` 输出绝对源时间的 transcript；render 消费映射到成片时间的字幕。新增 CLI `transcribe --source ... --out ...`。

    word_timestamps=True, vad_filter=True, beam_size=5,

- [ ] 字幕布局默认留出底部约 300px、右侧约 140px 的操作区余量（设计起点，不是平台官方安全区）；手机比例预览检查，不遮脸、不盖游戏关键字幕，必要时移到上下区域间的留白。
- [ ] app 按“选本地任务 → 看候选和中文解释 → 播放片段 → 改日语字幕/切点/ROI → 重新预览 → 确认导出”组织。无需时间线拖拽或账号系统。
- [ ] 默认只监听 `127.0.0.1`；朋友可在本机审核，或由你分享预览与审稿表。不要因为朋友在异地就自动公开服务器或传原片到云端。

## 后续阶段的触发条件

短片连续 20 条的验收/工时达到商业目标，且客户确有需求，再单独安排：

1. **视觉召回增强**：Task 3B 已包含多模态理解；若全场低频扫描仍漏掉短暂事件，再增加特定游戏事件检测或自适应加密采样。不能声称只看文字候选就覆盖了全片视觉高光。
2. **十分钟长片**：有独立报价后，支持多个片段按话题连接、原始横屏布局和承接文字。沿用 shots 时间映射；不得简单串 10 条互不相干 Shorts 后宣称完成长片。
3. **本地文本 LLM**：API 费用或素材出网要求成为实际瓶颈时，再测试 Qwen3-8B 量化模型，ASR 卸载后加载，测总显存和审片时间变化。
4. **全自动批处理**：固定主播版式稳定后增加本地文件夹串行扫描，生成草稿、质量报告和失败列表；用操作系统计划任务即可，不上消息队列。
5. **发布能力**：有明确平台、账号、素材授权和业务许可后另做计划。技术自动出片成功不等于允许无人审核公开发布。

不要在首轮实现这五项。先完成可出售的一条片子，并验证相同流程能处理第二场回放。
